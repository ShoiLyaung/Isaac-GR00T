## Finetune 失败原因

**1. Shard caching 慢（ffmpeg vs torchcodec）**
- m0-clean 默认 `video_backend="torchcodec"`，但 submodule 的 mp4 触发 `RuntimeError: Could not seek file to pts=0`
- 切到 `video_backend="ffmpeg"` 后，198 ep × 56 shard 的 ffmpeg 解码非常慢
- 8-10 分钟才能进入 step 1（vs M0 2-3 min）

**2. ffmpeg 单 step 慢**
- 1.55 it/s（vs M0 1.5-2.0 it/s）
- 总时长 1h 47m（vs M0 2h 58m，但 M0 跑 10000 steps 我们已完成）
- **注意**：ffmpeg 比 torchcodec 慢但**没慢太多**——M0 跑 2h58m 是因为同样的 shard 缓存机制 + 300 ep。**真正的瓶颈是 sharded_single_step_dataset 的预缓存机制**（任何 backend 都得缓存 56 个 shard）

**3. stdout 缓冲误导**
- 进度 bar 用 `\r` 覆盖同一行
- nohup 重定向 log 时 Python stdout 默认 block-buffered
- 8-10 min 看不到任何 log 输出 → 误以为卡住
- 实际进程在跑，loss 在下降（最终看到 step 125 loss=1.07）

**4. 误杀**
- 因 log 看起来"卡住"被 kill -9
- 实际是误判，进程本来在跑

## 决策与原因

**用户决定：接受 M0-R baseline，不继续 submodule finetune。**

理由：
1. M0-R 已经证明：pipeline 可跑 + wrapper 正确 + 机器人能动。0.0/10 success 是 task 难度本身。
2. Submodule 比 M0 多出的信息（effort 列、1 个真实 task 描述）**不太可能突破 task 难度天花板**。
3. Submodule finetune 需要 ~2h 慢跑（无明显收益）。
4. 0/198 episodes 的视频缺失（submodule Stage 2 只保留 198/300 ep）已经减少统计功效。

## 关键发现（可应用于未来）

1. **GR00T loader 的 tasks_map 索引 bug**：
   - `tasks_map = {task_index (int): task_desc (str)}`
   - 但 lookup 用 `x` 是 string
   - 解决方法：tasks.jsonl 用 string key
2. **GR00T loader video path 占位符**：只支持 `{episode_chunk}` / `{video_key}` / `{episode_index}`，不支持 `{file_index}`
3. **sharded_single_step_dataset 预缓存 N shards in memory**：N = total_steps / shard_size，启动慢
